# Phase Objective

Build the canonical real-interview intelligence and knowledge feedback system for Interview Explainer.

The system must connect:

```text
REAL INTERVIEW
   ↓
PRIVATE REFLECTION
   ↓
OPTIONAL CONTRIBUTION
   ↓
PRIVACY REVIEW
   ↓
ANONYMIZATION
   ↓
MODERATION
   ↓
NORMALIZATION
   ↓
CANONICAL QUESTION MATCHING
   ↓
EVIDENCE RECORD
   ↓
COMPANY / ROLE / ROUND INTELLIGENCE
   ↓
PREPARATION IMPROVEMENT
   ↓
BETTER FUTURE INTERVIEWS
```

The system must not become:

* an anonymous rumor board,
* a Glassdoor clone,
* a Reddit clone,
* a random interview-question dump,
* a platform for publishing confidential interview material,
* a place where one person's experience becomes a universal claim,
* a fake company interview database,
* an SEO page generator based on thin user submissions,
* an uncontrolled community forum,
* or an AI system that invents company-specific interview patterns.

The central product principle is:

```text
USER REPORT
      ≠
VERIFIED FACT
      ≠
CANONICAL QUESTION
      ≠
COMPANY-WIDE INTERVIEW PATTERN
```

These are separate knowledge layers.

---

# Core Knowledge Architecture

```text
PRIVATE INTERVIEW EXPERIENCE
          ↓
OPTIONAL CONTRIBUTION
          ↓
CONTRIBUTION RECORD
          ↓
MODERATION
          ↓
EVIDENCE RECORD
          ↓
NORMALIZATION
          ↓
CANONICAL KNOWLEDGE LINK
          ↓
AGGREGATED INTELLIGENCE
          ↓
PREPARATION SYSTEM
```

The system should preserve the difference between:

```text
WHAT ONE USER REMEMBERS

WHAT MULTIPLE USERS REPORTED

WHAT THE PLATFORM CAN
REASONABLY INFER

WHAT THE PLATFORM
ACTUALLY KNOWS
```

---

# Critical Architectural Boundary

Do not build one overloaded entity called:

```text
INTERVIEW QUESTION
```

The system needs separate concepts:

```text
CANONICAL QUESTION
      ↓
A reusable preparation object

REPORTED QUESTION
      ↓
What a contributor remembers being asked

QUESTION EVIDENCE
      ↓
Evidence connecting a report to a canonical question

INTERVIEW EXPERIENCE
      ↓
The broader interview event

COMPANY INTERVIEW SIGNAL
      ↓
An aggregated pattern derived from evidence
```

Example:

```text
CANONICAL QUESTION

"How does HashMap work internally?"
```

A user may report:

```text
"They asked me how HashMap works
and then asked about collisions."
```

Another may report:

```text
"Explain HashMap internals,
hash collisions and Java 8 changes."
```

These should not automatically become three separate canonical questions.

They may become:

```text
CANONICAL QUESTION
HashMap Internal Working

EVIDENCE 1
Reported at Company A
Backend Engineer
Technical Round
June 2026

EVIDENCE 2
Reported at Company A
Java Developer
Technical Round
May 2026
```

This is the foundation of reliable interview intelligence.

# The Most Important Knowledge Distinction

The platform must distinguish:

```text
1. USER MEMORY

"I remember being asked this."

2. MODERATED REPORT

"A contributor reported being asked this."

3. CORROBORATED SIGNAL

"Multiple independent contributors
reported similar questions."

4. AGGREGATED PATTERN

"Available recent evidence suggests
this topic appears in interviews
for this role."

5. CANONICAL PREPARATION KNOWLEDGE

"This is a well-defined interview topic
the user should understand."
```

The system must never jump directly from:

```text
ONE USER REPORT
```

to:

```text
THIS COMPANY ALWAYS ASKS THIS.
```

# Evidence Graph

The long-term architecture should behave like:

```text
COMPANY
   │
   ├── ROLE
   │     │
   │     ├── INTERVIEW STAGE
   │     │      │
   │     │      ├── EVIDENCE
   │     │      │      ↓
   │     │      │   REPORTED QUESTION
   │     │      │      ↓
   │     │      │   CANONICAL QUESTION
   │     │      │
   │     │      └── TOPIC SIGNAL
   │     │
   │     └── PREPARATION BLUEPRINT
   │
   └── COMPANY INTERVIEW INTELLIGENCE
```

This allows the same canonical question to be supported by:

```text
MULTIPLE COMPANIES
MULTIPLE ROLES
MULTIPLE INTERVIEW STAGES
MULTIPLE TIME PERIODS
MULTIPLE INDEPENDENT REPORTS
```

without duplicating the question itself.

# Example

Suppose three users report:

```text
USER A
Company: Nutanix
Role: Backend Engineer
Round: Technical
Time: June 2026

"They asked how ConcurrentHashMap works."
```

```text
USER B
Company: Nutanix
Role: Software Engineer
Round: Java Technical
Time: May 2026

"Difference between HashMap and
ConcurrentHashMap and internal working."
```

```text
USER C
Company: Another Company
Role: Java Developer
Round: Technical
Time: June 2026

"How does ConcurrentHashMap achieve
thread safety?"
```

The platform should not create:

```text
QUESTION 1
How ConcurrentHashMap works

QUESTION 2
HashMap vs ConcurrentHashMap

QUESTION 3
How ConcurrentHashMap achieves thread safety
```

without checking existing canonical structure.

It may map them to:

```text
CANONICAL QUESTION A

How does ConcurrentHashMap work internally
and achieve thread safety?

RELATED QUESTION B

HashMap vs ConcurrentHashMap
```

Then preserve evidence:

```text
QUESTION A
   ├── Nutanix / Backend / Technical / June 2026
   ├── Nutanix / Software Engineer / Java Round / May 2026
   └── Other Company / Java Developer / Technical / June 2026
```

Now Interview Explainer can say:

```text
Recent contributor reports indicate that
ConcurrentHashMap has appeared in technical
interviews for Java/backend roles.

For Nutanix-specific evidence, similar
questions were reported by multiple
contributors in the available dataset.
```

It should not say:

```text
NUTANIX ALWAYS ASKS
CONCURRENTHASHMAP.
```
